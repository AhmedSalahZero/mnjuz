# Subsystem: tests-infra


## summary

The tests-infra subsystem is a PHPUnit 10.3.4 / Laravel 10.23.0 / PHP 8.4.25 suite (Mockery available, no Pest, no paratest, no CI config: `.github/workflows`, `.gitlab-ci.yml`, `Makefile` all absent; no `composer test` or npm test script). It runs against a dedicated MySQL database `mnjuz_testing` (root/salah) declared in `/media/salah/Software/projects/mnjuz/phpunit.xml:27-32` and duplicated in `/media/salah/Software/projects/mnjuz/.env.testing`; `tests/CreatesApplication.php:17-31` force-copies the phpunit.xml `<env>` values into `$_ENV`/`$_SERVER` before bootstrapping so the suite can never accidentally run against the dev copy of production (`.env` → `appmnjzn`, 817,356 contacts / 3,278,056 chats / 235 organizations). Almost every DB test uses `RefreshDatabase` (Laravel: `migrate:fresh` once per PHP process — measured 33.8–35.0 s — then one rolled-back transaction per test); `QUEUE_CONNECTION=sync`, `CACHE_DRIVER=array`, `SESSION_DRIVER=array`, `MAIL_MAILER=array`, and `BROADCAST_DRIVER` is unset so it resolves to `null` (`config/broadcasting.php:18`). There are 92 PHP test files (21 Unit, 71 Feature incl. 5 `Feature/Cycle` webhook→job→DB round-trip tests and 10 `Feature/MobileApi`), ~1,185 test methods, plus 17 node `.mjs` tests of pure JS composables under `tests/js` (9 wrapped by PHP tests, 8 orphaned). External APIs are never HTTP-mocked (zero `Http::fake` in the suite): tests rely on guard clauses that return before the network, `Bus::fake([...])` for `ProcessMediaDownloadJob`/`ProcessAutoReplyJob`, `Event::fake([NewChatEvent::class])`, and Mockery only for Waz billing services. Baseline measured today: full suite `php artisan test` = 1165 passed, 18 failed, 1 skipped, 4,777 assertions in 164.84 s; all 18 failures are pre-existing auth-route drift unrelated to messaging.

## current_flow

- `php artisan test` → PHPUnit reads `phpunit.xml` (`bootstrap="vendor/autoload.php"`, suites `Unit`=`tests/Unit`, `Feature`=`tests/Feature`; `<php><env>` block lines 21-48: `APP_ENV=testing`, `BCRYPT_ROUNDS=4`, `CACHE_DRIVER=array`, `DB_CONNECTION=mysql`, `DB_HOST=127.0.0.1`, `DB_PORT=3306`, `DB_DATABASE=mnjuz_testing`, `DB_USERNAME=root`, `DB_PASSWORD=salah`, `MAIL_MAILER=array`, `QUEUE_CONNECTION=sync`, `SESSION_DRIVER=array`, `TELESCOPE_ENABLED=false`).

**2. Getting a database**
- Tests declare `use RefreshDatabase;` (66 of 92 files; see inventory in the tests section). Laravel 10.23 semantics: first test in the process runs `migrate:fresh` on `mnjuz_testing` (only `database/migrations`, 152 files; measured ~34 s), sets the static `RefreshDatabaseState::$migrated`, then every test runs inside `beginDatabaseTransaction()` and is rolled back in tearDown. No seeding anywhere (`grep '$seed\|->seed('` → none).
- Module migrations are NOT auto-loaded (`grep loadMigrationsFrom modules app` → nothing). `modules/FlowBuilder/Database/Migrations` (4 files: flows, flow_user_data, flow_logs, flow_media) and `modules/Webhook/Database/Migrations/2024_09_26_080857_create_webhooks_table.php` are run only by tests that explicitly ask:

## risks

- **Global uniqueness on `chats.wam_id_active_key`** (`mnjuz_testing` also has `chats_wam_id_unique (wam_id)`; prod only the virtual one): it is unique across all organizations and channels. Telegram `message_id` (small integers), Messenger `mid`, TikTok ids are not globally unique across bots/pages → inserts would collide across orgs, and `MessageStatusCycleTest.php:130-143` shows status matching is by wam_id + org. New channels must namespace the stored id (e.g. `tg:<chat_id>:<message_id>`) or the schema needs a `(channel, external_id)` unique; no existing test covers this.
- **`Contact::firstOrCreate([organization_id, phone => null])`** matches ANY phone-less contact in the org (`ContactWithoutPhoneTest.php:121-135` documents the bug); if the channel resolver falls through to the WhatsApp path, all Telegram/Messenger users of an org merge into one contact and their chats interleave — silent data corruption, not an error.
- **Schema drift between test DB and production**: tests validate migrations against a fresh `migrate:fresh`, but prod has three tables/indexes with no repo migration (`team_working_hours`, `webhook_events`, `webhooks` from a module; index sets on `contacts`/`chats` differ; testing has two extra UNIQUE keys prod lacks). Migrations that `dropUnique`/`dropIndex` by name or assume column widths 191 will pass tests and fail in prod (or vice-versa). Every new migration must be additive and guarded (`Schema::hasColumn`, `hasIndex`), with defaults (`channel` default `'whatsapp'`) so 3.2 M existing chats / 817 K contacts need no backfill under lock; a `NOT NULL` add without default or an `ALTER` that rebuilds `chats` (mediumtext metadata) is a multi-minute lock on prod.
- **`QUEUE_CONNECTION=sync`**: jobs execute inline inside the test transaction, so queue ordering, retries, `release()`, deadlocks (`CampaignFailedGroupDeadlockTest` only greps the source for the retry count) and out-of-order webhook delivery are never really exercised; the status "ladder" tests pass because delivery is sequential. Channel drivers with different ordering guarantees (Telegram has no receipts; Messenger sends `delivery`/`read` with watermarks not ids) need explicit unit tests of the mapping, not just cycle tests.
- **DDL inside a transaction**: any new test that runs `artisan migrate` in `setUp()` after `RefreshDatabase` began the transaction (as `FlowFirstMessageTriggerTest.php:42` does) commits the transaction and leaks rows into later tests in the same process; put channel tables in `database/migrations` or follow `CycleTestCase::refreshTestDatabase()`.
- **Real network calls in tests**: org metadata uses `access_token 'test-token'`, so any path that reaches `WhatsappService` send / Graph download performs a real HTTPS call to graph.facebook.com and swallows the failure (e.g. `InboundSideEffectsTest.php:146-157` passes trivially with 0 == 0 outbound; `OutboundSendCycleTest.php:126-139` comment admits a guard regression would be masked). Offline CI turns these into slow timeouts. New drivers must be `Http::fake`-able; otherwise Telegram/Messenger tests will hit real endpoints with fake tokens.
- **Source-string guard tests** (`ContactWithoutPhoneTest:246-262`, `MessageSenderNameTest:182-204`, `MobileReactionFilterTest:177-198`, `CampaignEmptyAudienceTest:340-352`, `CampaignFailedGroupDeadlockTest:213-233`, `CampaignHistoryMediaTest:286-296`, `MediaRetryAndLocaleVersionTest:27`, `DeletedTemplateTest:248`, Vue regex tests) will break on legitimate refactors; deleting them instead of updating them removes the only protection for several production bugs they encode.
- **Single shared MySQL DB** (`mnjuz_testing`) and `migrate:fresh` at the start of every process: two concurrent `php artisan test` invocations (or `--parallel`, which is not installed) corrupt each other. Never point `DB_DATABASE` at `appmnjzn`: `CreatesApplication.php:20` only re-forces `mnjuz_testing` when the env var differs, and editing `phpunit.xml` removes that protection — a wrong value would drop the 3.2 M-row dev copy.
- **Mobile response contract**: `MobileSyncRawRowsTest` and `MessageSenderNameTest` pin key sets (`user` must be exactly `['full_name']`, message block keys fixed); adding channel fields inconsistently between v1/v2/broadcast surfaces as a green suite but a broken app; every added key must be documented for the mobile developer.
- **Baseline is not green** (18 pre-existing failures); without fixing them, a channel regression in the auth area or a new failure count of 19 could go unnoticed.
