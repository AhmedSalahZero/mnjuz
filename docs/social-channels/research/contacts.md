# Subsystem: contacts


## summary

The contacts subsystem is the identity table for everything else (chats, tickets, campaigns, flows, ratings) and today its identity is a phone number: `contacts.phone` (E.164) plus the virtual `phone_active_key` unique index per organization. Reads go through `App\Models\Contact` (search scope, chat-list query `contactsWithChatsOptimized`, `lastChat`/`lastInboundChat` relations, phone masking for agents) and are serialized by `ContactResource` (web contacts page + mobile `/api/v1/contacts`), `ContactListResource` (chat sidebar), and the raw model in `getContactDetail`. Writes go through `ContactService` (web/mobile create/update/delete + `findOrCreateByPhone` used by every "send to phone" endpoint), `ContactsImport` (queued via `ProcessContactsImportJob`), `ProcessContactSyncJob` (WhatsApp coexistence sync), and the inbound WhatsApp jobs (`ProcessIncomingMessageJob::getOrCreateContact`, `ProcessMessageEchoJob::getOrCreateContact`), all of which key on `(organization_id, phone)`. A `ContactObserver` normalizes phone to E.164 and fills `formatted_phone` on every save; `PhoneService` wraps libphonenumber + a Brazil helper. Cross-cutting consumers (`ChatBroadcastPayloadBuilder`, `ChatNotificationContentBuilder`, `ActivityLogger` labels, `TemplateTrait`, FlowBuilder, `WhatsappService::isSendableNumber`, block/unblock via Graph) all read `$contact->phone`/`formatted_phone_number`, and most already tolerate NULL (fallback to `'-'`, `'Unknown'`, or skip) because NULL-phone contacts have existed in production before (see `tests/Feature/ContactWithoutPhoneTest.php`). There is no `channel` column, no `external_id`, and no Contact factory; the model is `$guarded = []` with `$timestamps = false` (created_at/updated_at set manually everywhere).

## risks

- **NULL-phone collapse (data corruption)**: `Contact::firstOrCreate([... 'phone' => null])` or `where('phone', $null)` becomes `WHERE phone IS NULL` and returns the first channel contact in the org — merging strangers' conversations (documented in `tests/Feature/ContactWithoutPhoneTest.php:121-135`; the same shape exists at `app/Jobs/ProcessIncomingMessageJob.php:199-218`, `app/Jobs/ProcessMessageEchoJob.php:110-129`, `app/Jobs/ProcessContactSyncJob.php:244-257`, `app/Services/ContactService.php:50-53, :107-110`, `app/Imports/ContactsImport.php:365-377`). Every channel path must key on `(organization_id, channel, external_id)`; never let a driver hand a NULL/empty phone to any of these. Add a unit test that a Telegram inbound never matches a NULL-phone WhatsApp contact and vice versa.
- **Duplicate channel contacts under concurrency**: inbound webhooks for the same user can be processed by parallel queue workers; without the `(organization_id, channel, external_id_active_key)` unique index plus the 1062 catch-and-reselect (pattern at `ProcessIncomingMessageJob.php:213-222`) you will get two contacts per user. Ship the index in the same deploy as the driver code.
- **Migration on production (817K contacts / 3.2M chats)**: `ADD COLUMN ... DEFAULT` and virtual generated columns are INSTANT/INPLACE in 8.4; adding the two secondary indexes is online but IO-bound — run off-peak and `LOCK=NONE`; avoid `Schema::table()->change()`, `->enum()`, or anything on `phone` (a COPY rebuild would lock inserts and webhooks would time out/retry). Prior art: `database/migrations/2026_05_31_000002_...` ran the same virtual-column pattern in prod.
- **Web edit of channel contacts breaks today**: `app/Http/Requests/StoreContact.php:32-38` requires phone → 422 for any Telegram contact edit; and `ContactService::store` (:128-130) would write `getE164Format(null)` = NULL phone (harmless) but if the client sends a phone it silently converts a channel contact into a phone contact. - **ActivityLogger labels** become NULL for nameless channel contacts (all `?: $contact->phone` sites) — activity pages show blanks.
