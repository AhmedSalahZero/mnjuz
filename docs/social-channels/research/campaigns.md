# Subsystem: campaigns


## summary

The campaigns subsystem is a WhatsApp-only bulk *template* sender. A user picks an APPROVED Meta template + a contact group (or "all"), fills header/body/button variables (static or contact-field dynamic), optionally uploads header media, and schedules it. `CampaignService::store` persists a `campaigns` row (status `scheduled`, `metadata` JSON of the chosen parameters). The scheduler runs `CreateCampaignLogsJob` every minute (queue `campaign-logs`) which materialises one `campaign_logs` row per audience contact and flips the campaign to `ongoing`; `ProcessCampaignMessagesJob` runs every 5s (queue `campaign-messages`) and dispatches at most `campaigns.send_batch_size` (10) `ProcessSingleCampaignLogJob`s per organization per tick. Each single job claims an idempotent slot in `campaign_message_attempts` (unique on `campaign_log_id, channel, attempt_number` — `channel` already exists, hard-defaulted to `'whatsapp'`), builds the Meta template payload via `TemplateTrait::buildTemplateRequest`, calls `WhatsappService::sendTemplateMessage` (which requires `contact.phone`, POSTs to Graph, creates the `chats` row and `chat_logs`, fires `NewChatEvent`), then writes `campaign_logs.chat_id/status/metadata`. Delivery status is *not* stored on campaign_logs: it is derived by joining `chats.status` (accepted/sent/delivered/read/failed) which the WhatsApp status webhook (`ProcessMessageStatusJob`) updates; a webhook `failed` also calls `CampaignRetryService::handleWebhookFailure` which flips the log to `failed` and schedules `RetryCampaignLogJob` (org-configurable hour intervals, WhatsApp error-code aware). Everything from validation (`settings.whatsapp` gate in the Vue form), through audience (no channel filter), message building (Meta template components), sending (`WhatsappService`), status (Graph status ladder), retry (Graph error codes 131xxx), to UI (`WhatsappTemplate.vue` preview, phone column) assumes WhatsApp + phone number + template. The `campaign_message_attempts.channel` column and the org-level retry settings are the only pieces already channel-aware; the legacy `SendCampaignJob` is dead code (only referenced from the uncalled `CampaignService::sendCampaign()`), and the external `ApiController::storeCampaign` is an empty stub. The mobile API (v1) has no campaign endpoints, only `/list-templates` and campaign *settings* via `MobileSettingController`.

## risks

- **Audience widening (data pollution + quota burn)**: today `CampaignAudienceService::query` has no channel filter (`:24-37`). The moment channel contacts exist with `phone = NULL`, every existing WhatsApp campaign flow would insert `campaign_logs` for them, claim `campaign_message_attempts`, hit `isSendableNumber` (`WhatsappService.php:470-478`) and record a failure, then `scheduleNextRetry` up to `max_retries` times and finally `moveContactToFailedGroup` — i.e. Telegram contacts would be silently moved into the "failed campaign" group and stripped from their other groups (`CampaignRetryService.php:356-380`). The channel filter must ship in the same release as the contacts `channel` column, and the WhatsApp filter must match the backfilled default exactly.
- **Group-scoped audience has no organization guard** (`CampaignAudienceService.php:32-36`) — unchanged risk, but adding a channel filter there must not accidentally add cross-org rows.
- **Attempt uniqueness**: the idempotency guarantee is `(campaign_log_id, channel, attempt_number)`. If new drivers pass a *different* channel string than the one used by `resolveAttemptNumber` (`:209-221`), attempt numbering restarts at 1 and duplicates can be sent; both must read `campaigns.channel`. Do not change the default `'whatsapp'` value on the column (existing 100% rows depend on it).
- **`chats.wam_id` uniqueness** (`wam_id_active_key` virtual unique): drivers that create outbound `chats` rows must produce globally unique ids; Telegram `message_id` is per-chat and small integers — a raw value would collide across contacts and abort the send with a QueryException *after* the provider already delivered (message sent, log marked failed, retry → duplicate delivery). Prefix with channel + peer id.
- **Status vocabulary**: `Campaign::getCounts` and `ProcessMessageStatusJob::applyStatus` assume `accepted<sent<delivered<read<played`. Drivers that write any other status string will make sent/delivered counters 0 and `resendableLogIds` mis-classify. Normalise in the driver, not in SQL.
- **Retry classification**: `NON_RETRYABLE_ERROR_CODES` and `extractFailureReason` are Graph-specific; leaving them generic means every Telegram error (`ok:false, error_code:403 "bot was blocked by the user"`) is treated as retryable → repeated sends to blocked users. Per-driver `classifyFailure` is mandatory before enabling retries on new channels.
- **Messaging window**: templates bypass the 24h window today, so the campaign pipeline has zero window logic. Free-form Messenger/Instagram/TikTok sends outside the window are rejected by the platform (and repeated violations get pages restricted). The pre-send check must run inside Phase 1 (`ProcessSingleCampaignLogJob.php:46-101`) using `contact.last_inbound_chat_created_at` and must *not* schedule retries that will predictably fail; also the `resetStuckOngoingLogs` 15-min reset (`ProcessCampaignMessagesJob.php:64-78`) flips such logs to `failed` and would re-enter the retry loop.
- **Locking/queues**: Phase 1 takes `lockForUpdate` on `campaign_logs` and inserts the attempt; the external HTTP call runs outside the TX (`:107-109`) — keep this for new drivers (Telegram file uploads can take seconds). `RetryCampaignLogJob` is `ShouldBeUnique` on `logId-retryIndex` with `uniqueFor 3600`; the job queue is `database` (`config/queue.php:16,33-39`, `after_commit => false`) so `->afterCommit()` on dispatches is load-bearing — do not remove.
- **Rate limits**: one global tick dispatches `send_batch_size` per org; if a new channel's driver is slower or has stricter global limits (Telegram ~30 msg/s bot-wide across *all* orgs), a per-channel cap must be enforced or the platform will 429 and every log will be marked failed+retried. `withoutOverlapping(4s)` on a 5s tick means a slow tick delays all channels.
- **`template_id` nullability**: `Campaign::template()` is used unguarded in `CampaignTable.vue:114`, `View.vue:66`, `CampaignDetailsExport.php:33`, `CampaignController.php:48-50` (search whereHas is fine), `TemplateTrait::buildTemplateRequest:13`. Any null must be guarded first or the list page 500s for the whole org.
- **`CampaignResource` N+1 / heavy counts** (`:18,26-29`): each row triggers `Contact::count`, `deliveryCount`, `readCount` queries; adding a channel filter is fine but do not add more per-row queries.
- **`SendCampaignJob` dead path**: if anything ever dispatches it (`CampaignService::sendCampaign`), it bypasses attempt claiming for the first send (`:224-258`) and uses the deadlock-prone failed-group move (`:377-402`). Safest is to delete it in the same change or leave untouched; do not "modernise" it.
- **Schema changes on production**: `campaigns` (~2K rows), `campaign_logs` (unknown but likely millions since 1,937 campaigns × audience), `campaign_message_attempts` — adding a column with default is an instant metadata change on MySQL 8.4 (`ALGORITHM=INSTANT`) for `campaigns`; for `campaign_logs` prefer `ALTER ... ADD COLUMN ... , ALGORITHM=INSTANT` and avoid adding indexes on it during peak; the existing `idx_campaign_logs_chat_id` migration pattern (`2026_08_03_...`) with `indexExists` guard should be copied.
- **`Organization::toArray` redaction** only strips `whatsapp.access_token` and `ai.api_key` (`app/Models/Organization.php:32-40`); the create page passes the whole org row to the browser (`CampaignController.php:58`). New channel tokens (Telegram bot token, page tokens) **will leak** to the client unless the redaction is extended before the settings tabs land.
- **Tests are source-guard heavy**: `CampaignEmptyAudienceTest.php:340-352`, `CampaignFailedGroupDeadlockTest.php:213-233`, `CampaignHistoryMediaTest.php:286-296`, `CampaignMediaPreviewTest.php:50-137`, `CampaignVideoHeaderTest.php:171-180` assert literal strings/regexes in `CreateCampaignLogsJob.php`, `StoreCampaign.php`, `CampaignRetryService.php`, `CampaignService.php`, `CampaignForm.vue`, `WhatsappTemplate.vue`, `templateMediaPreview.js`. Refactors must preserve those exact snippets (e.g. `CampaignAudienceService::query(` in the job, the `}, 5);` deadlock retry, the `$metadata['header']['format'] = $header['format'];` ordering, `<WhatsappTemplate ... :placeholder=` in the form) or update the tests deliberately.

`campaign_logs.metadata` success example: `{"data":{"messaging_product":"whatsapp","contacts":[{"input":"+9665...","wa_id":"9665..."}],"messages":[{"id":"wamid.HBg...","message_status":"accepted"}]}}`; failure example: `{"data":{"error":{"message":"...","type":"OAuthException","code":131026,"error_data":{"details":"..."},"error_subcode":...,"fbtrace_id":"..."}},"message":"<error_user_msg|message>"}`; no-phone example: `{"message":"This contact has no phone number."}` (`WhatsappService.php:477`).

## `campaign_message_attempts` row
`id, campaign_id, campaign_log_id, contact_id, channel(varchar30 default 'whatsapp'), attempt_number(smallint), is_retry(bool), status('ongoing'|'success'|'failed'), failure_reason(text), response_metadata(longtext json of same response object), executed_at, created_at, updated_at`; unique `cmp_attempt_unique(campaign_log_id, channel, attempt_number)`.

## `campaign_log_retries` row
`id, campaign_log_id, chat_id, metadata(json response or {"error":"..."}), status('ongoing'|'success'|'failed'), timestamps`.

## Web resources
- `CampaignResource` (`app/Http/Resources/CampaignResource.php:20-31`): `{id, uuid, name, template:<full Template row or null>, status, contacts_count, delivery_count, read_count, contact_group_count}`.
- View page props (`CampaignController::index:71-111`): `campaign` = Campaign row + `contact_group` + `template` + `total_message_count, total_sent_count, total_delivered_count, total_failed_count, total_read_count`; `resendableCount`; `rows` = paginated `CampaignLogResource`: all `campaign_logs` columns (tz-converted timestamps) + `contact` (Contact row incl. appended `full_name`, `formatted_phone_number`) + `chat` (Chat row + `logs[]` ChatStatusLog rows) + `attempts[] {id, attempt_number, channel, is_retry, status, failure_reason, executed_at, response_metadata}`.
- Media history endpoint: `GET /campaigns/media-history?type=IMAGE` → `{data:[{uuid,name,path,media_type,size,created_at}]}`; `DELETE` → `{success:true}` or 404 `{message}`.
- Export CSV columns: `Campaign Name, Template, First Name, Last Name, Phone Number, Last Updated, Status`.
