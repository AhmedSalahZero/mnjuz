# Subsystem: chat-ui-web


## summary

The web chat UI is an Inertia page (`resources/js/Pages/User/Chat/Index.vue`) served by `app/Http/Controllers/User/ChatController.php`, which is a thin wrapper over `app/Services/ChatService.php` (list, thread, send, template, location, block, clear). The contact list is built by `Contact::contactsWithChatsOptimized` (app/Models/Contact.php:213-338) and serialised by `app/Http/Resources/ContactListResource.php`; the open conversation is serialised by `ChatService::contactPayloadForChatView` (1377-1412) plus `app/Helpers/MessagingWindowHelper.php` (24h window). The thread is a `chat_logs` timeline (`ChatService::getChatMessages` 1132-1184) whose `chat` entries carry the raw `chats` row (metadata = WhatsApp-shaped JSON string) rendered by `ChatBubble.vue`; realtime updates arrive on presence channel `chats.ch{org}.{user}` via `NewChatEvent` (payload from `app/Services/Chat/ChatBroadcastPayloadBuilder.php`) and are merged by `mergeChatIntoThread.js`. Sending goes through `ChatService::sendMessage` -> `WhatsappService` (text via `SendTextMessageJob`, media via `SendMediaJob` on queue `high`), templates through `CampaignForm.vue` -> `/chat/{uuid}/send/template`. The same `ChatService::getChatList` is also called by the mobile API (`app/Http/Controllers/ApiController.php:2047`), so list-shape changes are mobile-visible. The UI is WhatsApp-only in three places that matter: the 24h window gate + template fallback (`ChatForm.vue`, `Chat24HourComposeBanner.vue`, `MessagingWindowHelper`), the composer's media limits/attach actions, and the phone-number identity (`openByPhone`, `formatted_phone_number`, `encryptPhoneNumber`, ActivityLogger fallbacks). Everything else (timeline, bubbles given canonical metadata, albums, unread, tickets, categories, search UI, virtual list, pagination, broadcast merge) is already channel-agnostic.

## required_changes

## Data / model (additive)
1. `contacts`: add `channel` VARCHAR(20) NOT NULL DEFAULT 'whatsapp' and `external_id` VARCHAR(191) NULL (+ `display_handle`/username optional); unique index `(organization_id, channel, external_id_active_key)` mirroring the existing `phone_active_key` pattern; index `(organization_id, channel, latest_chat_created_at)` for the filtered list. Add `channel`/`external_id` to every select list: app/Models/Contact.php:228-241, app/Services/ChatService.php:267-282, app/Services/Chat/ChatBroadcastPayloadBuilder.php:343-346.
2. `chats.wam_id`: keep the column; each driver must write a namespaced platform id (e.g. `tg:<chat_id>:<message_id>`, `fb:<mid>`, `ig:<mid>`, `tt:<id>`) because `wam_id_active_key` is unique and Telegram message ids are per-chat integers. Optionally add `chats.channel` (default 'whatsapp', denormalised from contact) so status jobs/webhooks can route without a join.
3. `Contact` model: add `getDisplayIdentifierAttribute()` (formatted phone for whatsapp, handle/external id otherwise) and use it in ActivityLogger fallbacks (ChatController.php:154,216,247,285; ChatService.php:577,624,707), `encryptPhoneNumber` (guard NULL phone, Contact.php:417-425), ChatForm `contactName` fallback.
4. `Contact::scopeSearchTerm` (69-105): when digits-only also `OR external_id LIKE`, and always `OR display_handle LIKE`; accept an optional `$channel` to scope.

## risks

- `chats.wam_id` unique index (`wam_id_active_key`): non-namespaced platform ids (Telegram `message_id` restarts per chat; Messenger `mid` vs Instagram `mid` could collide) would either throw duplicate-key on insert (message lost) or make `mergeChatIntoThread` replace a different bubble. Namespace ids per channel.
- `contactsWithChatsOptimized` is the hot path over 817K contacts; adding `where channel = ?` without an index on `(organization_id, channel, latest_chat_created_at)` degrades the ordered pagination; adding the column with a DEFAULT on MySQL 8.4 is INSTANT, but creating the index and the new unique virtual-column index on 817K/3.2M rows must be run ONLINE (ALGORITHM=INPLACE, LOCK=NONE) off-peak.
- `Chat::created` hook updates `contacts.last_inbound_chat_created_at`; `MessagingWindowHelper` derives the 24h gate from it for ALL contacts. If the helper is not made channel-aware first, Telegram contacts silently become un-messageable after 24h and the banner pushes agents to WhatsApp templates that cannot be sent.
- `ensureChatTicketsExist` (ChatService.php:1186-1219) inserts tickets on GET for any contact with `latest_chat_created_at`; new-channel contacts will get tickets automatically (desired) but the 500-row cap means bursts show untouched contacts without `ticket_status` on the first load.
- Mobile shares `ChatService::getChatList` (ApiController.php:2047) and the JSON branch returns `ContactListResource` (316-320); any new key or changed `phone` semantics ships to the app at once. Also `ChatBroadcastPayloadBuilder` output is reused by mobile sync; keys must be added, never renamed.
- Inertia partial reloads use fixed `only:` lists (ChatTable.vue:105,195; ChatHeader.vue:166; Index.vue:480). New props (e.g. `channels`, `filters.channel`) not in those lists keep stale values after a filter visit; put `filters` (already included) as the carrier and keep `channels` static.
- `encryptPhoneNumber` (Contact.php:417-425) runs on every open conversation for agents with encryption on: `Str::mask(null, '*', 4)` on a NULL phone — verify it does not throw on PHP 8.4 before shipping non-phone contacts.
- Block/Unblock (ChatHeader.vue:221-226 -> ChatService::blockContact) would call the WhatsApp block API for a Telegram contact; must be capability-gated or it errors/misreports.
- `sendAuthTemplate` (ChatController.php:194) merges `phone => null` for non-WhatsApp contacts and forwards to the API controller; must be blocked at the capability layer.
- `lastChat` relation filters `metadata not like '%"type":"reaction"%'`; a driver storing reactions under another type key will make reactions the list preview again (regression already fixed for WhatsApp, see LastChatPreviewTest).
- Structural tests read the Vue sources (`tests/Unit/ChatBubbleRenderChainTest.php`, `ChatThreadHiddenTypesTest.php`, `ChatAttachmentUploadTest.php`, `tests/Feature/ChatMediaAlbumTest.php`, `ChatThreadMergeTest.php`): renaming `RENDERED_TYPES`/`SILENT_TYPES`/`HIDDEN_CHAT_TYPES`, moving the paste/drag listeners, or moving `mergeChatIntoThread` will fail CI even if behaviour is intact.
- Queue ordering: text goes through `SendTextMessageJob` and media through `SendMediaJob`/`Bus::chain` on queue `high`; per-channel drivers must keep running inside those jobs (or equivalent) so the optimistic bubble/`tempMessageId` handshake and the `NewChatEvent` `tempMessageId` echo keep working; a driver that responds synchronously without broadcasting leaves the optimistic bubble stuck at `sent`.
- `Request()->has('is_read')` (Contact.php:283) treats any value as the unread filter; a channel filter that appends `is_read=` accidentally would hide read chats.
- `getChatMessages` route `/chats/{contactId}/messages` has no organization check (ChatController.php:299-305); adding channel does not fix that, but any refactor should not widen it.
- Session-scoped `chat_sort_direction` and URL-scoped filters are per-user, not per-channel; acceptable but note that switching channel keeps ticket/unread/category filters.
- Contact identity decision (one contact per channel) means `openByPhone` from a shared contact card (ChatController.php:47-72) always lands on the WhatsApp contact; that is consistent with the owner's decision but must be documented for agents.
