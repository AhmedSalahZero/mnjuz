A prior design memo exists at repo root `SOCIAL_CHANNELS_REPORT.txt` (Arabic, 2026-09-11) proposing a Channel Driver layer; it assumed identity unification and no campaigns — both now decided the other way.

## risks

- **Global message-id uniqueness**: `chats_wam_id_unique` (`2026_05_31` migration L72, virtual `wam_id_active_key`) plus the org-agnostic cache key `wam_processed_{id}` (`ProcessIncomingMessageJob.php:255-279`) mean Telegram `message_id` integers (1, 2, 3… per chat) would silently drop messages across orgs/chats as "duplicates". Namespace ids per channel before insert; never reuse raw provider ids.
- **Contacts unique key**: `(organization_id, phone_active_key)` — adding channel contacts with `phone = NULL` is safe, but any code that later "fills in" a phone on a Telegram contact (e.g. `ContactService::store:128-130`, `ContactObserver`) could collide with the WhatsApp contact of the same number (owner decided they are separate people) → guard phone edits by channel.
- **Schema changes on 3.2M chats / 817K contacts**: `ADD COLUMN … DEFAULT` is INSTANT on MySQL 8.4; adding indexes is online but long — run off-peak, never `CHANGE`/`MODIFY` existing columns (`chats.status` was already altered once, `2025_01_29`). Do not touch `phone_active_key`/`wam_id_active_key` definitions.
- **Queued-job signature changes**: jobs are serialised with ctor args; adding parameters must be trailing with defaults (`ProcessIncomingMessageJob($message,$contactData,$organizationId)`, `ProcessMessageStatusJob($statuses,$organizationId)`) or in-flight jobs on `high`/`messageStatus` fail after deploy.
- **Locking/ordering**: campaign sends rely on `lockForUpdate` on `campaign_logs` (`SendCampaignJob:228-231`, `ProcessSingleCampaignLogJob`) and the `campaign_message_attempts` unique claim (`ProcessSingleCampaignLogJob:44`); a new driver must be called in "phase 2 (no TX)" exactly like WhatsApp (`ProcessSingleCampaignLogJob:107`, `RetryCampaignLogJob:144`) or DB locks are held during HTTP calls. Status ladder guard (`ProcessMessageStatusJob:36-41`) must stay; drivers emitting `read` before `delivered` are fine, `failed` after `delivered` is ignored by design.
- **Window gate regressions**: `MessagingWindowHelper` is called from 11 sites; making it channel-aware via the `Contact` (not a global switch) avoids opening WhatsApp composes after 24h. The client-side duplicate in `ChatForm.vue:461-480` will keep blocking Telegram composes unless updated in the same release.
- **Token leakage**: `Organization::toArray` redacts only `whatsapp.access_token`; Inertia sends `settings` (org metadata) to `Whatsapp.vue`, `CampaignForm.vue`, `Templates/Add.vue`, `Dashboard.vue`. New channel secrets stored under `organizations.metadata` must be redacted the same way or they ship to the browser.
- **Mobile app hard whitelist**: `ChatStatus::SUPPORTED` and the app's `type` switch — unknown `status` is dropped to `null` (`ChatStatus::forApi`), unknown metadata `type` falls into the app's default branch. Keep new channels inside existing enums; a NULL `phone`/`formatted_phone_number` was flagged by the prior memo as the riskiest mobile change (`Contact::encryptPhoneNumber:417-425` does `Str::mask($this->phone…)` — guard NULL).
- **Pusher 10 KB limit** (`ChatBroadcastPayloadBuilder::fitToPusherLimit`): adding `channel`/`external_id` is small, but do not add avatar URLs or raw provider payloads to the broadcast value.
- **Rate limits / subscription gating**: `WebhookController:163 isLimitReached` (message quota) and `SubscriptionService` checks are applied only in the WhatsApp intake — replicate in new intakes or quotas are bypassed.
- **Translation keys are English sentences**: `MessagingWindowHelper:81/92`, `WhatsappConnectionHelper:29/41`, `ChatService:1270` etc. Changing the text changes the key → Arabic falls back to English. Add new keys instead.
- **Hard-coded Graph versions** (`v18.0` at `WebhookController:305`, `ProcessMediaDownloadJob:272`; `v20.0` at `MetaService:27`) — Messenger/IG drivers should read one config value.
- **Signature verification is disabled** (`WebhookController:87-94`); enabling it for Meta while adding Messenger/IG changes behaviour for existing WA webhooks — gate per route.
- **Chat::created hook** (`Chat.php:21-32`) issues a `contacts` UPDATE per message (`latest_chat_created_at`, `last_inbound_chat_created_at`); higher inbound volume from new channels multiplies row-level write contention on hot contacts — unchanged behaviour but capacity planning.
- `resources/js/Pages/User/Settings/General.vue:530` posting to `/settings/whatsapp` may break when that route becomes tabbed — verify what it submits.
