# Subsystem: mobile-api


## summary

The mobile API is the `/api/v1` group in `routes/api.php:71-204` (Sanctum + `has.mobile.app` + `check.active.organization` + `check.has.selected.organization`), plus a legacy bearer-token public API at `/api/*` (`routes/api.php:36-69`, `AuthenticateBearerToken`) that shares the same `App\Http\Controllers\ApiController` methods. The organization always comes from `users.current_mobile_organization_id` (no session in the `api` group; `MobileApi` trait `organizationId()` at `app/Http/Controllers/Api/Concerns/MobileApi.php:22-25`, and `$request->is('api/v1/*')` branches all over `ApiController`). Chat data reaches the app three ways: REST sync (`GET /list-messages-from-uuid-to-end` v1/v2, `ApiController.php:2088-2375`, built from `chat_logs` → `chats` raw rows via `loadChatSyncData`/`loadChatRows`/`formatChatValue`), Pusher/Reverb presence channel `chats.ch{org}.{user}` (`NewChatEvent` → `ChatBroadcastPayloadBuilder::buildMinimalValue`, same JSON as REST), and FCM push (`SendNewChatPushNotificationJob` + `ChatNotificationContentBuilder`). Sending from mobile is entirely WhatsApp: `/send-msg` (text → `WhatsappService::sendMessage` → `SendTextMessageJob`; files → `ChatService::sendMessage` → `SendMediaJob` chain), `/chats/upload/chunk` → `SendMediaJob`, `/send-template`, `/send-auth-template`, `/request-location`, `/send-location`; every one of them resolves the contact **by phone** (`ContactService::findOrCreateByPhone`), checks `WhatsappConnectionHelper`, and enforces the 24h `MessagingWindowHelper`. The newer sub-controllers under `app/Http/Controllers/Api/` (tickets, profile, settings, automation, reports, support tickets, broadcast-config) are channel-agnostic except that ticket items expose `phone` and settings expose the WhatsApp `auth_template`.

## risks

- **Null `phone` reaching the installed app**: `MOBILE_CHAT_EXAMPLES.md:38` promises `phone` non-null; a Kotlin/Swift model with non-null `phone` will crash on Telegram contacts. Keep the key, coordinate nullability (or send `""`) with the mobile dev before shipping; same for `formatted_phone_number`, and FCM `data.phone` (`SendNewChatPushNotificationJob.php:74` already casts to string, so `""`).
- **500 on `/api/v1/contacts` for agents**: `ContactResource.php:23` → `Contact::encryptPhoneNumber` → `Str::mask(null…)` throws when `tickets.encrypt_contacts_for_agents` is on and a contact has `phone = NULL`.
- **Wrong-channel sends**: `SendTextMessageJob` / `SendMediaJob` are hard-wired to `WhatsappService`; dispatching them for a phone-less contact fails silently in the queue (`isSendableNumber` false → logged, no chat row, app shows nothing). The channel must be resolved **before** dispatch; never rely on the phone to infer the channel.
- **`chats.wam_id` uniqueness**: unique virtual key `wam_id_active_key`; platform ids from Telegram (`message_id` is per-chat, small ints), Messenger (`mid.…`), Instagram, TikTok can collide with each other or across orgs → duplicate-key exception = lost inbound message. Prefix ids per channel (`tg:<chat_id>:<message_id>`), verify length ≤ 128.
- **Inbound rows must be `Chat::create` + `chat_logs`**: bulk `insert` skips the `created` hook (`Chat.php:21-32`) so `latest_chat_created_at`/`last_inbound_chat_created_at` (sync ordering, window, `unread`) break; a chat without a `chat_logs` row never appears in the mobile sync (`loadChatSyncData:2656-2667`).
- **Metadata contract**: the app switches on `metadata.type` (`MOBILE_MESSAGE_TYPES.md` §5); storing platform-native JSON (Telegram `update`, Graph `messaging[]`) instead of the WA-shaped envelope renders empty bubbles and breaks `ContactListResource::metadataPreview`, `ChatNotificationContentBuilder`, and `visibleChatsQuery`'s reaction filter.
- **Status semantics**: `ChatStatus::forApi` nulls unknown statuses; Telegram has no delivered/read, TikTok/IG have their own — map to `sent/delivered/read/failed` or the app shows no ticks; `chat_status_logs.metadata` must keep `{id,status}`.
- **Pusher 10KB shrink** (`ChatBroadcastPayloadBuilder.php:192-211`): adding fields grows the payload; keep `channel` short and do not let the shrink steps drop it (the app needs it to pick the icon).
- **Sync query performance at 817K contacts / 3.2M chats**: the channel filter must hit `contacts` (indexed) not `chats.metadata`; `loadChatSyncData` already does `getCountForPagination` + `whereExists` — adding `where channel` without an index on `(organization_id, channel, latest_chat_created_at)` will regress `/list-messages-from-uuid-to-end` (already logs >4MB responses, `:2211-2220`).
- **Queue contention**: all sends, broadcasts and push share queue `high`; slow third-party APIs (Telegram file upload, TikTok) can delay WhatsApp broadcasts — consider per-channel queue names or timeouts inside the drivers, keep WA on `high` unchanged.
- **Ordering of media batches** relies on `Bus::chain` (`ChatService.php:854-917`) and `continueBatchOnFailure`; a driver that throws non-recoverable exceptions can stop the chain — preserve the semantics tested by `MobileMediaBatchTest`.
- **Templates/auth codes**: `/send-auth-template` is used for verification codes; sending it to a non-WA contact must fail loudly (422), not fall through to WA with a null phone.
- **Cross-tenant gaps to not extend**: `markAsRead:3390`, `toggleTicketStatus:3202`, `assignContactToUserThroughTicket:3352` use `Contact::find` without org scoping (pre-existing); the new channel filter/driver code must scope by organization.
- **Source-text tests**: `MobileReactionFilterTest.php:280-301` asserts exactly 3 occurrences of `visibleChatsQuery` in active `ApiController` source and forbids `Chat::query()->with('media','user','logs')`; `:319-329` asserts the exact comment layout in `getChatMessages:3025-3031`. Any refactor of `ApiController` must keep these or update the tests deliberately.
- **v1/v2 parity test** (`MobileSyncRawRowsTest.php:626-652`): every key in the v2 message block must exist with the same value in v1.
- **Doc drift**: `MOBILE_MESSAGE_TYPES.md:1402-1423` describes a text-send shape that the code no longer produces (`ApiController.php:936-938` forces the queued shape); confirm the app's current parser before adding fields to `data`.
- **Bearer public API** (`/api/send*`, `/api/contacts`) shares `ApiController` methods: keep `channel` defaulting to `whatsapp` when absent so external integrators are unaffected; `config/apiguide.php` need not change.
- **Data loss**: no mobile endpoint alters schema; only `clearContactChat` soft-deletes. The only destructive risk is the `wam_id` unique collision above and a driver that "creates" contacts by phone for a non-phone channel (would fabricate WA contacts).

(`last_chat` only when relation loaded — not in this endpoint.) `GET /contacts/{id}` → `data` = raw `contacts` row (all columns incl. `phone`, `formatted_phone`, `avatar`, `address`, `metadata`, `is_blocked`, `is_favorite`, `latest_chat_created_at`, `last_inbound_chat_created_at`, `created_at`, `updated_at`) + `full_name`, `formatted_phone_number`, `chat_ticket`, `contact_groups`, `contact_categories`, `groups[{id,name}]`, `categories[{id,name,background_color,text_color}]`.
`POST /contacts` body: `first_name`(req), `phone`(req, E.164-valid, unique in org), `last_name?`, `email?`, `file?`, `street/city/state/zip/country?`, `metadata?` (array), `is_blocked?`, `group[]?` (ids), `categories[]?` (ids) → `{"statusCode":200,"success":true,"data":{"uuid":"…"},"message":"Request processed successfully"}`; duplicate → 400 `{…,"data":[],"message":"This phone number already exists","errors":{"phone":[…]}}`. `PUT /contacts/{id|uuid}` same fields optional. `DELETE` → `{"statusCode":200,"success":true,"data":[],"message":…}`.

### send-msg — `POST /api/v1/send-msg` (multipart or JSON)
Request: `phone` (req, E.164), `type` (`text` → text path when no file), `message` (text body; becomes caption with files), `first_name?`,`last_name?`,`email?` (used when the contact is auto-created), `header?`,`footer?`,`buttons?` (WA interactive), `file`|`files[]` (≤ `chat.max_batch_files`=10, mimes list at `ApiController:1395`), `caption?`, `msg_uuid?` (string or array, one per file).
Text response (queued): `{"statusCode":200,"success":true,"message":"Message queued for sending.","data":{"queued":true,"contact_id":1,"contact_uuid":"…","phone":"+9665…"}}`.
Files response: `{"statusCode":200,"success":true,"message":"Message sent successfully","data":{"queued":true,"files":2,"contact_id":1,"contact_uuid":"…","phone":"+9665…"}}`.
Errors: 400 `{"statusCode":400,"success":false,"message":"The provided data is invalid.","errors":{"phone":[…]|"file":[…]}}`; 400 size `{…,"message":"File is larger than the :size limit."}`; 403 subscription / WhatsApp not connected `{"statusCode":403,"success":false,"message":…}`; 422 window `{"statusCode":422,"success":false,"message":"Whatsapp does not allow sending messages 24 hours after they last messaged you. However, you can send them a template message"}`; 422 batch `{"statusCode":422,"success":false,"message":…}`.
Chunk upload: `POST /chats/upload/chunk` fields `upload_id,index,total,chunk,phone,file_name,file_type?,caption?,msg_uuid?,first_name?,last_name?` → progress `data{completed:false,received,total}`; final `data{completed:true,queued:true,received,total,contact_id,contact_uuid,phone}`; `DELETE` → `data{discarded:true}`.
