# Subsystem: automation


## summary

The automation subsystem is the auto-response pipeline that runs after an inbound message has been stored as a `chats` row. `ProcessIncomingMessageJob` dispatches `ProcessAutoReplyJob` (queue `autoreplies`), which gates on subscription message limit + organization working hours, then calls `AutoReplyService::checkAutoReply()`. That runs an org-configurable sequence (`organizations.metadata.automation.response_sequence`, default `['Basic Replies','Automated Flows','AI Reply Assistant']`) where the first responder that sends wins: (1) Basic Replies (`auto_replies` table, keyword match -> text/image/audio/location_request), (2) Automated Flows (`modules/FlowBuilder` — node graph in `flows.metadata`, per-contact state in `flow_user_data`, sends text/media/interactive buttons/CTA-URL/interactive list, plus non-messaging actions), (3) AI Reply Assistant (`modules/IntelliReply` — OpenAI chat/whisper/TTS, sends text or audio). Every one of these send paths instantiates `App\Services\WhatsappService` directly from `organizations.metadata.whatsapp` and calls `sendMessage()` / `sendMedia()`; there is no channel abstraction anywhere. Adjacent WhatsApp-only features in scope: Working-Hours away notice (`SendTextMessageJob` -> `WhatsappService::executeSendMessage`), Ice Breakers + WhatsApp Commands (synced to Meta `conversational_automation`, meaningless on other channels). `modules/WorkingHour/*` is dead/unwired reference code (wrong namespaces, not in composer autoload, migration not registered); the live implementation is `app/Services/WorkingHoursService.php` + org metadata `working_hours`.

## required_changes

### A. Introduce a channel-driver seam (the single most important change)
1. **`App\Contracts\MessageChannel` (or `ChannelDriver`) interface** with at least: `sendText(Contact, string $body, ?int $userId=null): SendResult`, `sendMedia(Contact, string $mediaType, string $fileName, string $path, string $url, string $location, ?string $caption=null): SendResult`, `sendChoices(Contact, string $body, array $options /* [{id,title}] */, array $opts /* header, footer, label */): SendResult`, `supports(string $feature): bool` (features: `interactive_buttons`, `interactive_list`, `cta_url`, `location_request`, `audio`, `markdown`), `name(): string`. `SendResult` must expose `success`, `chat` (the created `Chat` model, needed by `FlowExecutionService.php:634-639` and `AIResponseService.php:184-187`), `error`.

## risks

- **Constructor side effects**: `FlowExecutionService`, `ActionExecutionService` and `AIResponseService` build `WhatsappService` eagerly; `WhatsappService::__construct` reads Pusher settings (see `tests/Feature/MarketingOptOutTest.php:41-45`) and needs `metadata.whatsapp`. `AutoReplyService::replySequence` (`:133`) instantiates it for `hasActiveFlow()` on every inbound message. If the resolver throws for orgs that have Telegram but no WhatsApp config, **every** inbound message's auto-reply job fails (3 tries, `:22`) — make resolution lazy and null-safe.
- **Silent WhatsApp regression**: all sends check `$response->success === true` and `$response->data->chat->id`. If the WhatsApp adapter changes the return object shape, `FlowLog` rows stop being created (`FlowExecutionService.php:634-639`) and `flow_logs_count` in the flows list (`Flow::listAll` `:29`) silently freezes; AI `isSuccessfulResponse` (`:184-187`) returns false and the sequence falls through to nothing. Keep the stdClass contract or adapt both call sites in the same change.
- **Phone-less contacts in flows**: with the `empty($contact->phone)` guard (`FlowExecutionService.php:489-497`) a non-WhatsApp contact enters a flow (`flow_user_data` row created at `:131-136`) and then every message node returns false without deleting the session; the contact is stuck in "Automated Flows only" mode forever (`AutoReplyService.php:139-141` forces the sequence when `hasActiveFlow` is true), so Basic Replies/AI never run for them. Must be fixed with the channel guard before enabling new channels.
- **Duplicate replies / ordering**: `ProcessAutoReplyJob` is not unique (imports `ShouldBeUnique` but doesn't implement). Two inbound messages from the same contact processed concurrently on the `autoreplies` queue race on `flow_user_data.current_step` (`FlowExecutionService.php:426,679,763,787`) with plain `update` calls and no locking; Telegram/Messenger webhooks deliver bursts more often than WhatsApp. Consider `WithoutOverlapping` keyed by contact, or a per-contact lock around `processFlow`.
- **Delayed flow + messaging window**: `ProcessDelayedFlowJob` (`ShouldBeUniqueUntilProcessing`, `uniqueId flow_{id}_contact_{id}`) resumes with a mock chat and empty message (`continueDelayedFlow` `:374-381`); on Messenger/Instagram a delay > 24h will fail at the platform, and since `processMessageNode` returns false without deleting `flow_user_data`, the contact stays stuck in the flow.
- **`flow_user_data` is per-contact with no org scope** (`:54`); fine given "one contact = one channel", but if contact IDs are ever merged/reused across channels the state leaks.
- **Chat metadata contract**: if a new channel stores inbound text under a different key (e.g. `{type:'message',text:'...'}`), `extractTextFromChat` returns `''` and `checkMatch(' ', trigger,'contains')` for Arabic triggers does `strpos(' ', word)` -> false, so no reply, silently. AI's `extractLastMessage` (`:602`) reads the **latest** chat for the contact, so an outbound row written by a new driver with an unexpected shape yields `message=null`.
- **`markInboundAsRead` on any automated reply** (`AutoReplyService.php:183-185`) marks ALL inbound of the contact read — same behaviour on new channels; the unread counter semantics for Telegram/Messenger chats will match WhatsApp (already flagged by `app/Console/Commands/DiagnoseUnreadChats.php`).
- **`update_contact` writing `phone`** (`ActionExecutionService.php:167,204`) on a channel contact can violate `(organization_id, phone_active_key)` uniqueness -> exception -> `executeAction` catches and returns false -> `DELETION POINT 4` deletes the session (`FlowExecutionService.php:694-698`). Not data loss, but a confusing dead end; gate it.
- **Away notice cache key** (`ProcessIncomingMessageJob.php:316`) is per contact, so one notice per channel contact — acceptable under "separate contacts".
- **Media reply files**: Basic Replies store `file.location` as local `public/...` path or S3 URL and derive `'local' vs 'amazon'` by string prefix `'public\\'` (`AutoReplyService.php:361`, note the backslash — on Linux paths are `public/...` so it always evaluates to `'amazon'`; WhatsApp path tolerates it because `sendMedia` uses `$mediaUrl`). New drivers that need a local file (Telegram multipart upload) must not rely on `location`.
- **Migrations**: FlowBuilder module migrations are not run by `php artisan migrate` (`database/migrations/2026_09_10_130000_*:88-89`); any new flow/auto-reply column must be added via `database/migrations` with `Schema::hasColumn` guards like the two 2026_09_10 files. `flows.trigger` is a MySQL ENUM altered by raw `ALTER TABLE` (`2026_09_10_120000_*:26-29`) — avoid further ENUM churn; use a nullable string/JSON `channels` column if scoping is added.
- **Source-text tests**: `tests/Feature/ContactPlaceholderEmptyValueTest.php:250-266` asserts on the literal text of `AutoReplyService.php` (`substr_count("if (\$message === '') {") === 2`) and of `ProcessIncomingMessageJob.php`; refactoring `sendReply` will break this test unless the two guards are preserved verbatim. `tests/Feature/MarketingOptOutTest.php:300-320` and `FlowBuilderEdgeScopeTest.php` also grep Vue/PHP source.
