===========================================================
  تذاكر الدعم في التطبيق - ما تحتاج معرفته
  آخر تحديث: 2026-09-19
===========================================================


أولاً: انتبه - عندنا نوعان من "التذاكر"
-----------------------------------------------------------

1) تذاكر المحادثات     GET /api/v1/tickets
   حالة محادثة عميل: مفتوحة أو مغلقة، ومسندة لموظف.
   موجودة من قبل ولم تتغير.

2) تذاكر الدعم          GET /api/v1/support-tickets
   طلب يفتحه المستخدم لفريق الدعم عندنا.
   هذه هي الجديدة، وكل ما في هذا الملف عنها.

لا علاقة بينهما. جدولان مختلفان و endpoints مختلفة.


ثانياً: الفكرة الأساسية
-----------------------------------------------------------

التذكرة تعيش في نظامين:

   تطبيقك  ->  قاعدتنا (items)  ->  واز أعمال (waz_tickets)
                                          ^
                                    هنا يعمل فريق الدعم فعلاً

قاعدتنا نسخة. واز هو مكان العمل الحقيقي، وهو مصدر الحقيقة
للحالة والردود.


ثالثاً: شاشة القائمة
-----------------------------------------------------------

   GET /api/v1/support-tickets?page=1&per_page=10

استدعاء واحد يعطيك كل ما تحتاجه:

   items          = تذاكر المستخدم عندنا
   waz_tickets    = نفسها كما يراها فريق الدعم
   waz_available  = هل الاتصال بنظام الدعم قائم الآن
   categories     = الفئات (للقائمة المنسدلة)
   statuses       = الحالات المسموحة
   priorities     = الأولويات المسموحة
   pagination     = page / per_page / total / last_page

* اقرأ waz_available قبل أي شيء:

  - true   اعرض waz_tickets، ففيها الحالة الحقيقية.

  - false  اعرض items وحدها، واكتب سطراً للمستخدم:
           "تعذر الاتصال بنظام الدعم، الحالة قد تكون غير محدثة"

  لا تفرغ الشاشة عند false. التذاكر موجودة، والمتعذر هو
  قراءة حالتها المحدثة.

* categories و statuses و priorities تأتيك جاهزة في نفس
  الرد. لا تكتبها في كود التطبيق ولا تستدعيها من مكان آخر.


رابعاً: لا تحاول ربط القائمتين
-----------------------------------------------------------

هذا أكثر ما يقع فيه الخطأ هنا.

   items[].uuid      ->  "3b1f-..."    معرفنا نحن
   waz_tickets[].id  ->  1042           معرف واز

نظامان مختلفان، ولا يوجد مفتاح مشترك يصلك حالياً.
لا تطابق بينهما بالعنوان ولا بالتاريخ.

و waz_tickets[].url رابط صفحة التذكرة عند الدعم - افتحه في
المتصفح إن أردت.


خامساً: إنشاء تذكرة
-----------------------------------------------------------

   POST /api/v1/support-tickets

   {
     "category": 2,
     "subject": "فاتورة غير صحيحة",
     "message": "المبلغ المخصوم أكبر من المتوقع"
   }

الثلاثة مطلوبة. category رقم من قائمة categories.
subject و message حد كل منهما 1024 حرفاً.

الرد يحمل التذكرة كاملة ومعها:

   "synced_with_support": true

   - true    اعرض: "تم إرسال تذكرتك"
   - false   اعرض: "حفظت تذكرتك، وقد يتأخر وصولها للدعم"

*** مهم جداً ***

التذكرة محفوظة في الحالتين. false ليست فشلاً، بل تعني أن
المزامنة مع نظام الدعم تأخرت.

لا تضع زر "إعادة المحاولة" عند false. كل ضغطة تنشئ تذكرة
جديدة عندنا وعند الدعم. الأمر يعالج من طرفنا.


سادساً: التعليق وتغيير الحالة والأولوية
-----------------------------------------------------------

   POST /api/v1/support-tickets/{uuid}/comment
   { "message": "ما زالت المشكلة قائمة" }

   POST /api/v1/support-tickets/{uuid}/status
   { "status": "closed" }

   POST /api/v1/support-tickets/{uuid}/priority
   { "priority": "high" }

* الـ uuid يؤخذ من items حصراً.

* تذكرة من waz_tickets لا uuid لها، فلا تعليق عليها ولا
  تغيير لحالتها من التطبيق.

* القيم المقبولة هي ما يصلك في statuses و priorities،
  وغيرها يرجع 400.

* رد التعليق يحمل التذكرة مع comments محدثة، فلا تحتاج
  استدعاء GET بعده.


سابعاً: عرض تذكرة واحدة
-----------------------------------------------------------

   GET /api/v1/support-tickets/{uuid}

نفس حقول التذكرة، ومعها comments:

   {
     "id": 5,
     "message": "ما زالت المشكلة قائمة",
     "seen": true,
     "created_at": "2026-09-19 11:02:00",
     "user": { "id": 9, "name": "أحمد صلاح", "is_me": true }
   }

* is_me تغنيك عن مقارنة المعرفات: اعرض الرد يميناً أو
  يساراً بحسبها.

* فتح التذكرة يعلم ردودها مقروءة تلقائياً. لا تحتاج
  استدعاء منفصلاً لذلك.


ثامناً: تنبيهان مهمان
-----------------------------------------------------------

(أ) التعليق من التطبيق لا يصل فريق الدعم

    المزامنة مع واز تحدث عند إنشاء التذكرة فقط. التعليق
    يحفظ في قاعدتنا ولا يراه أحد من الدعم.

    هذا سلوك النظام القائم، والويب يفعل الشيء نفسه.

    ما يجب فعله في التطبيق الآن: إما ألا تعرض حقل التعليق،
    أو تكتب تحته بوضوح "ملاحظة داخلية - لا تصل فريق الدعم".

    الأسوأ أن يكتب العميل مشكلته وينتظر رداً لن يأتي.


(ب) synced_with_support لا تعود في الجلب

    تصلك مرة واحدة في رد الإنشاء فقط.

    أما GET /support-tickets فلا يخبرك أي تذكرة وصلت الدعم
    وأيها لا.

    (نحفظ المعرف عندنا عند نجاح المزامنة، ونستطيع إرجاعه
     في الرد إن احتجته - أخبرنا.)


تاسعاً: الصلاحيات
-----------------------------------------------------------

   GET  /support-tickets            الجميع - تذاكره هو فقط
   GET  /support-tickets/{uuid}     صاحب التذكرة
   POST /support-tickets            الجميع، بمن فيهم الموظف
   comment / status / priority      صاحب التذكرة

* لا شرط باقة على أي منها.

* تذكرة مستخدم آخر ترجع 404 لا 403، عمداً، كي لا يستدل
  على وجودها.


عاشراً: الأخطاء المتوقعة
-----------------------------------------------------------

   400   حقل ناقص
         فئة غير موجودة
         حالة أو أولوية خارج المسموح

   401   بلا token أو منتهٍ

   404   تذكرة غير موجودة أو ليست لك

تفاصيل الحقول تأتي في errors، ونص message مترجم وجاهز
للعرض مباشرة.
